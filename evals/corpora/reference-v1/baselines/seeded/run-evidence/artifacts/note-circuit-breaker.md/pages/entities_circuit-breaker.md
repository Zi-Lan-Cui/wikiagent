# 熔断器

熔断器是一种核心保护机制，当下游服务已不可用时，它会主动停止向上游发送请求，从而避免消耗上游资源并阻碍下游服务的恢复。其决策周期被设计为需要覆盖重试的完整序列。

## 三态状态机模型

熔断器采用“闭合→打开→半开”的三态状态机进行工作。

1.  **闭合状态**：请求正常放行，同时系统统计失败率与慢调用率。
2.  **打开状态**：当任一统计指标超过预设阈值时，熔断器进入打开状态，直接拒绝所有请求。
3.  **半开状态**：打开状态持续一段时间后，熔断器进入半开状态，此时会放行少量探测请求。只有连续多次探测请求成功，熔断器才会恢复至闭合状态；若失败则重新打开。探测请求本身不参与重试机制。

## 关键参数

文档中给出的熔断器关键参数如下：

-   **触发阈值**：失败率50%、慢调用率50%
-   **统计窗口**：30秒
-   **最小请求数**：20
-   **打开状态持续时间**：30秒
-   **半开状态探测策略**：每次放行1个探测请求
-   **恢复条件**：连续3次探测请求成功

## 决策依据

熔断器的判定基于下游服务的**整体健康状态**（如5xx错误和超时），而非单次请求的错误类型（例如429限流错误不会触发熔断）。当前的实现方式是每个服务实例独立进行熔断统计。

## 已知缺口

当前熔断器实现存在以下已知局限：

-   熔断策略与[[concepts/retry-mechanism|重试机制]]的预算未联动，可能导致恢复时所有实例同时放量，引发流量洪峰。
-   半开状态下的探测请求没有全局总量上限，可能对刚恢复的下游服务造成压力。
-   熔断打开期间积压请求的处理策略尚未统一。

熔断器有效性的最终评估标准应是观察其是否能够缩短下游服务的恢复时长。
