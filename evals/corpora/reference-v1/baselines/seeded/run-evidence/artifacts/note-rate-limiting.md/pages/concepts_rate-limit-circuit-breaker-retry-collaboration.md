# 限流-熔断-重试协作

在构建高可用分布式系统时，限流、熔断与重试是三种关键的弹性机制。它们各自解决不同的问题，但需要协同工作以形成有效的系统保护策略。

## 职责边界

这三种机制的核心职责明确区分，互不替代：

*   **限流**：控制进入系统的请求速率。其目标是保护服务免于过载，并按照契约分配资源配额。
*   **熔断**：判断下游服务的状态。当检测到下游故障或延迟过高时，熔断器会快速失败，避免请求堆积和资源浪费。
*   **重试**：处理单个请求的临时失败。它为因网络抖动或瞬时错误导致的失败提供自动恢复能力。

## 协作规则

当这些机制在同一请求链路上共存时，必须遵循明确的协作规则以确保系统行为的可预测性和效率。

1.  **尊重限流信号**：当下游服务返回 `429` (Too Many Requests) 状态码时，上游调用方必须尊重响应头中的 `Retry-After` 字段，主动降低请求速率。
2.  **避免无效重试**：被限流机制主动拒绝的请求（例如，网关返回 `429`）**不应**被重试。重试一个已被明确告知“过快”的请求是无效且有害的。
3.  **限流触发后的标准响应**：当限流机制触发时，系统应返回 `429` 状态码与 `Retry-After` 头，并持续监控被拒绝流量的趋势，以便调整限流策略。

## 交互模式

在典型的请求处理流程中，这三种机制按特定顺序发挥作用：

1.  请求首先经过[[entities/rate-limiter|限流]]层。如果速率超过阈值，请求被立即拒绝（返回 `429`）。
2.  通过限流的请求被发送到下游。如果下游服务故障，[[entities/circuit-breaker|熔断]]器可能打开，请求被快速失败。
3.  对于因网络瞬时问题等原因失败的请求，[[concepts/retry-mechanism|重试]]机制可以尝试重新发送（前提是该请求未被限流拒绝）。
