本文档是一份关于订单事件链路消息投递语义的技术笔记，其核心结论是投递语义理解错误会导致可靠性设计失效。文档首先系统阐述了三种基本投递语义：at-most-once（最多一次）、at-least-once（至少一次）和exactly-once（恰好一次），并指出在分布式系统中，exactly-once无法通过纯消息机制实现，必然是“at-least-once投递 + 幂等消费”的组合。基于此，订单域当前选择了at-least-once投递配合消费者幂等的方案。

为实现幂等消费，每条消息携带生产者生成的全局唯一`message_id`，消费者通过查询去重表来跳过重复消息，且去重记录与业务处理在同库同事务中提交。去重记录的TTL被设为7天，以覆盖消息系统最长72小时的重投窗口。

关于消息顺序，文档指出全局有序在MQ中不必要也做不到，应实现按业务键（如`order_id`）的有序。具体实现是通过哈希将同一订单的所有事件路由到同一队列分片，并在分区内由单消费者串行处理。其代价是热点订单可能阻塞整个分片，当前通过“按订单哈希 + 分区内并发上限”进行折中，但热点问题尚未根治。

在死信与重试机制方面，消费者处理失败后消息会进入重试队列（最多重投3次，采用指数退避策略），重试耗尽则进入死信队列。文档强调，9月事故的核心教训是死信队列依赖人工处理且缺乏监控，导致积压4小时无人发现。事故后新增了两条规则：必须对死信队列深度和积压时长进行监控告警，并需开发“一键重放”工具。

文档还强调了事件与状态的一致性原则：事件是“事实已发生”的通知，消费者在决策前必须回查状态库确认，以库为准，避免“事件先到、状态后到”的竞态。生产者的顺序约定是先在数据库提交状态变更，事务提交后才发送事件。

最后，文档列出了当前已知的三个缺口：死信处理自动化（监控告警已有，但“一键重放”工具未完成，且重放顺序未定）；exactly-once的边界未文档化（未明确“at-least-once + 幂等”等价于恰好一次的场景，以及对外部系统副作用调用等不等价场景的处理方向）；以及热点分区的流量倾斜问题（分区键再哈希一级的方案存在争议）。
