# 重试机制

重试机制旨在将暂时性故障从用户视角抹掉，但其固有副作用是每一次重试都在故障期间向下游额外发送流量，可能形成“重试风暴”。因此，设计需在提升成功率与保障可用性之间取得平衡。

## 设计框架

### 错误分类
错误分类是决定是否重试的第一道关口。只有暂时性故障才应重试，确定性失败则不应重试，因为重试只会放大调用量。

- **暂时性故障（可重试）**：连接失败、读取超时、503、502、429等。
- **确定性失败（不可重试）**：4xx格式错误、认证失败、业务规则冲突等。

超时被务实归入暂时性故障，但其模糊性引出了后续幂等问题。

### 幂等性
最关键的边界是“可重试≠可重复”。判断可重试性只看错误类型（如下游是否可能恢复），不看请求内容；操作的可重复性则依赖幂等保障。

- 重试机制按错误码决定是否重试，去重责任在调用方业务层。
- 写请求必须带幂等键。
- 对无幂等保障的写操作，超时后重试或报错都无免费正确答案，正确解法是补齐幂等。
- 不应在下游明确返回“请求已处理”后继续重试。

### 退避策略
退避参数控制重试的节奏与总量。当前设置为初始200ms、指数退避、单次等待上限5s、最多4次尝试（含首次）。

- 指数退避使重试节奏匹配恢复曲线。
- 上限封顶控制总耗时。
- 4次尝试定位为“救抖动，不救宕机”。
- 超限后返回最后一次错误原样，不包装新类型。

这套参数缺少随机抖动（jitter），导致了6月事故：所有客户端在固定时间点同步发起重试，重试流量整齐划一地砸在同一个瞬间，将库存服务打挂。复盘指出，指数退避解决“重试别太勤”，jitter解决“重试别扎堆”，两者缺一不可。修正方案为等待时长=计算值×random(0.5, 1.5)。事故还教训：分析流量异常时需将重试流量与业务流量分开看。

### 超时与预算
每次尝试必须有独立超时，且总等待时间必须有预算。当前参数下总等待约12-15秒，需从调用方整体等待预算中支出。当前已实现独立超时，但跨尝试的总deadline统一约束尚未实现。

实现层面需注意：
- 使用单调时钟进行退避计算。
- 记录每次尝试的日志以用于事后分析。
- 对退避结果进行上下界校验。

## 核心矛盾与结论

重试机制是解决特定问题的工具，需明确其职责边界，它更像一个[[concepts/mutual-exclusion-is-not-correctness|错误中继站]]，而非业务去重器。

最终结论沉淀为：
- 重试救暂时性故障，对确定性失败是纯伤害。
- 可重试性与可重复性由不同机制保障。
- 退避需指数、jitter和总预算三者齐备。
- 宏观上重试放大系数需全局预算和熔断兜底。

## 已知缺口
1.  随机抖动（jitter）尚未修复，修正方案已明确。
2.  全局重试预算缺失，无法控制宏观放大系数，方向是实例级或集群级重试配额。
3.  服务端Retry-After头未被处理。笔记特别澄清，Retry-After影响重试的“何时”，但不应影响“该不该”重试，后者只由错误分类加幂等保障共同决定。
