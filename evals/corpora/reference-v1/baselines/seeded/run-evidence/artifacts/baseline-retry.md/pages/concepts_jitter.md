# 随机抖动(jitter)

随机抖动（jitter）是一种在重试机制中引入随机性的策略，用于防止多个客户端在相同时间点同步发起重试，从而避免形成“重试风暴”或流量尖峰，导致下游服务瞬间过载。它是指数退避策略的必要补充，两者共同构成完整的退避节奏控制。

## 作用与必要性

当多个客户端遇到相同的暂时性故障并采用相同的指数退避参数时，它们会在完全相同的时间点重试，导致重试流量整齐划一地砸在同一个瞬间。这种“重试扎堆”现象会瞬间放大对下游服务的请求压力，可能将其打挂。引入随机抖动后，每个客户端的重试时间点会变得错开，使重试流量在时间上分散，从而更平稳地恢复。

## 与指数退避的关系

指数退避解决的是“重试别太勤”的问题，即随着重试次数增加，等待时间指数级增长，避免过于频繁地重试。随机抖动解决的是“重试别扎堆”的问题，即在指数退避计算出的等待时长基础上加入随机扰动，避免同步重试。两者缺一不可，共同确保重试流量在时间和空间上都是可控的。

## 具体实现方案

根据文档中明确的修正方案，实现随机抖动的方法是：将指数退避计算出的等待时长乘以一个介于0.5到1.5之间的随机数。公式为：
`等待时长 = 计算值 × random(0.5, 1.5)`
其中，“计算值”通常指根据指数退避策略（如初始等待时间、指数因子、重试次数）计算出的理论等待时长。`random(0.5, 1.5)` 表示一个在0.5到1.5之间均匀分布的随机浮点数。

## 实现注意事项

在实现退避计算（包括指数退避和抖动）时，需注意：
- 使用单调时钟进行退避计算，避免系统时间调整的影响。
- 记录每次尝试的日志，用于事后分析。
- 对退避结果进行上下界校验，确保等待时长在合理范围内。

## 相关概念

随机抖动是重试退避策略的一部分，与 [[concepts/exponential-backoff|指数退避]] 紧密相关，共同服务于重试机制的流量控制目标。
