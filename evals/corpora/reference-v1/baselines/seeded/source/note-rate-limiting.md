# 限流笔记（网关与订单服务）

> 背景：订单网关接入大促流量后，峰值是日常的 8 倍，直接把下游压垮过两次。2026-08 的事故：网关限流阈值是年初拍脑袋定的（全局限 5 万 QPS），大促当天 8 点整流量冲到 6 万，限流器触发——但触发方式是把所有超限请求直接拒掉，其中包含支付回调。客户付了钱、订单没建上，对账炸了三天。这篇笔记梳理限流的定位、算法选型，以及和熔断、重试的配合边界。

---

## 一、限流解决什么：保护与配额是两件事

限流有两个容易混用的动机，混用会做出错误设计：

- **保护**：防止流量打垮服务（下游的自我保护）。触发限流 = 服务已经或即将过载。
- **配额**：按契约分配资源（每个租户/每个调用方只能用这么多）。触发限流 = 对方用超了。

保护型限流的正确响应是"优雅拒绝+提示"，配额型限流的正确响应可能是"计费/降级/告警"。网关当前的限流是保护型。支付回调被拒的事故，根因就是把保护型限流做成了"无差别拒绝"——**保护型限流必须区分流量优先级**：核心链路（支付回调）即使超限也要放行，可延迟流量（报表拉取）优先拒绝。

## 二、算法选型：令牌桶与漏桶

两个主流算法，参数和语义完全不同：

- **令牌桶**：以恒定速率放令牌（如 100 个/秒），请求取令牌，取不到即拒绝。桶容量是**突发容忍度**——容量 300 意味着可以短时间放行 3 倍速率。适合"允许突发、平均受控"的场景。
- **漏桶**：请求进队列，以恒定速率流出。队列满即拒绝。**不允许突发**——超过流出速率的请求要么排队要么拒绝。

网关当前用令牌桶：速率按下游容量评估（库存 2 万 QPS、支付 5 千 QPS），桶容量 = 速率 × 2 秒，即允许 2 秒的突发。令牌桶参数的两个坑：速率要按"下游真实容量"定而不是按"上游想发多少"定；桶容量太大等于没限流，太小等于把突发全部拒绝。

## 三、分布式限流：精确 vs 成本

单实例限流只保护自己，N 个实例共享一个下游时，必须做**分布式限流**——全局速率上限。当前实现：Redis 计数（INCR + 过期），每秒一个窗口。

代价和误差都要说清楚：

- **误差容忍**：窗口计数法有边界误差（两个窗口交界处的突发会翻倍计数）。当前误差容忍 10%，即实际放行最多超限 10%。要更精确可以用滑动窗口或令牌桶的 Redis 实现，成本翻倍。
- **同步成本**：每个请求都要访问 Redis 计数——把 Redis 变成了新的单点。当前做了本地预扣：实例先按"配额/实例数"本地扣，超了再问 Redis 借。实测 Redis QPS 降到请求量的 5%。
- **故障兜底**：Redis 不可用时怎么办？当前策略是**放行**（fail-open）——限流失效比服务不可用危害小。这个取舍是订单域的选择，支付域反过来（fail-closed）。

## 四、限流与熔断、重试的配合（边界最乱的地方）

三个机制都出现在"流量控制"场景，职责边界：

- **限流管"我放多少过去"**：入口处的速率控制，请求还没发出就决定。
- **熔断管"对方还活着吗"**：发出后根据响应判断下游状态。
- **重试管"失败了再试几次"**：单请求维度的补偿。

429 是关键交互点：下游限流返回 429（可能带 Retry-After，见重试笔记）。上游收到 429 的正确动作是**尊重提示减速**，而不是熔断（429 是"有意识的拒绝"，不是故障）也不是盲目重试（重试笔记已写清：Retry-After 影响"何时"，不影响"该不该"）。

但有一个真实的坑：**上游限流器触发时，对被拒请求不要重试**。被限流拒绝的请求重试没有任何意义（限流条件没变），只会放大被拒流量。当前实现里被限流请求直接返回 429 给调用方，不进入重试队列——这条规则是 8 月事故之后加上的。

## 五、限流的位置：入口与出口

- **入口限流**（网关）：保护下游的"总量"，按调用方/路由维度计数。
- **出口限流**（服务自身）：保护自己不被打爆，按自身容量计数。

当前只有入口限流。出口限流的场景是"上游全部守规矩，但总量仍然超载"——比如 20 个上游每个都在自己的配额内，加起来还是把下游压死了。这个"集体超载"问题入口限流解决不了，只能靠下游自己的出口限流。缺口见第七节。

## 六、限流触发后的响应设计

拒绝本身不是终点，被拒的请求要有明确的响应契约：

- 返回 429 + Retry-After（当前固定 1 秒，TODO：按桶恢复速率动态计算）。
- 区分优先级：核心链路放行、可延迟流量拒绝（第一节的教训）。
- 监控被拒流量：被拒率突增 = 配额评估错了或上游有异常流量。8 月事故前被拒率一直在涨但没人看——被拒流量本身是要盯的指标。

## 七、已知缺口

1. **出口限流未实现**（最高优先级）："集体超载"没有防线。方向：下游服务自带容量限流，与网关入口限流形成双层。
2. **优先级分流无统一框架**：支付回调放行是硬编码的，路由表变一次改一次代码。方向：流量优先级配置化（核心/普通/可延迟三级）。
3. **限流与重试预算未联动**：限流触发后，上游实例的重试流量仍然照发（重试的是"被限流拒绝的请求"——第六节说好了不重试，但只对"本实例被拒"生效；其他实例的重试流量不会因为下游限流而收敛）。方向和熔断笔记第七节合并：限流状态广播给重试预算。

## 八、沉淀

- 保护型限流必须区分流量优先级，无差别拒绝会把核心链路一起杀死。
- 令牌桶的桶容量就是突发容忍度——按业务对突发的容忍度定，不是随便设。
- 分布式限流要在"精确"和"成本"之间选边，误差要显式写出来。
- 被限流拒绝的请求不重试——重试不会改变限流条件。
- 限流、熔断、重试是入口/下游/请求三个维度的机制，互相配合但绝不互相替代。
- 被拒流量本身是监控对象：被拒率趋势比限流器本身更能说明问题。
