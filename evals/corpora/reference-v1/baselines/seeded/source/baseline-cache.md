# 缓存失效策略笔记

> 背景：商品详情页读 QPS 太高，加了 Redis 缓存后，大部分问题从"怎么读得快"转移到了"怎么不失效错"。缓存失效是整个缓存体系中**出错最多、最难排查**的一环——缓存不命中只是变慢，失效错了却是读到脏数据，而且是"看起来一切正常"的脏数据。2026-05 的事故（价格已改但页面三天没更新）就是这个性质的问题，这篇笔记把当前实现、踩过的坑和已知缺口系统地整理一遍。

---

## 一、为什么失效策略如此重要

缓存的本质是用**一致性换取性能**：把库里的数据复制一份放在更快的介质上，就必然存在"库里的值"和"缓存里的值"不一致的时间窗口。我们的目标不是消灭这个窗口（做不到），而是：

1. **把窗口缩到业务可接受的范围**——价格显示 30 秒的旧值通常没关系，显示 3 天就是事故；
2. **让窗口有上界**——任何失效手段失败，都必须有一条兜底路径保证数据最终一致；
3. **让失效过程可观测**——"删除失败"这件事必须被看见，而不是悄悄变成一个永远没人发现的洞。

一个常被低估的事实是：**所有主动失效手段（删缓存、发事件、代际键）都会失败**。网络会抖动、消息会丢失、任务会重试到上限放弃、代码会有 bug。所以失效方案的真正重点不是"正常路径怎么删"，而是"失败路径怎么兜底、怎么发现"。

---

## 二、失效时序：两种基本方案及其缺陷

更新缓存的时序之争是经典问题。关键约束在于：**写数据库和删缓存是两个独立的操作，不可能是原子的**。既然不是原子的，并发就可能从两个操作之间的缝隙里钻过去。

### 2.1 先删缓存，后写库

```
线程A（写）: ─── 删除缓存 ─── 写数据库 ───>
线程B（读）:                    ─── 缓存未命中? 读库 ─── 回填旧值 ───>
```

缺陷：线程 A 删完缓存后、写入新值前，线程 B 读请求进来，发现缓存没有，直接穿透到库，**读到的是旧值，还顺手把旧值回填进了缓存**。之后 A 写完库，缓存里却已经躺着旧值了，直到下次过期才消失。

更糟的是，读回填旧值可以发生在删缓存之后的**任意时间点**——只要读发生在写完成之前，回填的就是旧值。所以这个方案的失效窗口实际上等于"写操作的全部耗时"，期间任何一个并发读都可能毁掉这次删除。

### 2.2 先写库，后删缓存

```
线程A（写）: ─── 写数据库 ─── 删除缓存 ───>
线程B（读）:                    ─── 缓存命中(旧值) ───>
```

缺陷一：写入后、删除前，其他读请求拿到的仍是旧值——但这个窗口非常短（通常只有毫秒级，就是删缓存那一下的耗时），业务上一般可以接受。

缺陷二（真正的风险）：**删除失败时旧值会一直残留**。如果删缓存的调用挂了（Redis 网络抖动、重启、超时），缓存里就是永久旧值——这正是 2026-05 事故的根因之一：删除失败进了重试队列，队列积压了没人管。

### 2.3 一个常见的思维陷阱：为什么不用"更新缓存"代替"删除缓存"

有人建议：写库后直接把新值写入缓存，不就不存在"读穿透回填旧值"的窗口了吗？理论上双写成功时确实如此，但：

- 写库和写缓存依然不是原子的，中间窗口仍然存在；
- **并发写写乱序**：两个写线程 A、B 按 A→B 的顺序写库，但缓存写入可能 B→A 到达（网络延迟不同），最终缓存里是 A 的旧值——**数据库明明是新值，缓存却回退了**，这种错误极难排查；
- 直接更新缓存要求缓存值能由写方廉价构造，很多场景读模型是多个表 join 出来的，写方构造一次比删了让读方重建还贵。

所以业界共识是**"失效而非更新"**：删除缓存，让下一次读来重建。读方是唯一权威的值构造者，天然避免了写乱序问题。

### 2.4 当前选择

**写库成功后删除缓存，删除失败记入重试队列由后台补删。** 选这个是因为它的不一致窗口最小（仅"写库完成 → 缓存删除完成"这一段），配合重试队列弥补"删除失败"的缺陷。5 月事故暴露的教训被固化为一条原则：

> **重试队列本身要有监控**——队列深度、积压时长、重试上限后进入死信的数量，全部要有告警。不然"删除失败"会变成"永远不删"，而且无人知晓。

## 三、TTL 兜底：最后的防线

### 3.1 TTL 不是失效手段，是失效失效之后的兜底

无论主动失效设计得多完美，总会有漏网之鱼：事件丢了、队列死了、代码漏改了某条更新路径。如果没有 TTL，这些漏网的条目就会**永久驻留**，直到被人工发现——5 月事故里价格旧值活了三天，说明当时的 TTL 也没能兜住（或根本没设）。

所以一条铁律：

> **即使主动失效 100% 成功，也必须给每条缓存设过期时间。** TTL 的存在理由不是性能，而是给一致性错误一个"自愈上界"。任何永久有效的缓存条目，都是一个潜在的 P0 隐患。

### 3.2 TTL 取值：按数据变化频率分级

统一用一个值不现实：

- 热点配置类（首页运营位、类目导航）：变化频率以天计，可以给长 TTL（如 30min～数小时），主要依赖主动失效，TTL 只兜漏；
- 业务数据（价格、库存）：变化频繁且业务敏感，TTL 要短，让"失效失败"的代价最小化；
- 参考值（订单域当前按 SKU 维度配置）：**价格类 5min、库存类 30s**。库存 30s 是因为超卖/超卖的容忍度最低；价格 5min 是平衡了变更传播速度和重建成本。

### 3.3 TTL 的副作用与配合手段

TTL 太短的问题：热点 key 频繁过期 → 频繁穿透到库重建 → 数据库压力。TTL 太长的问题：失效失败的代价大。所以 TTL 需要和下一节的重建锁、空值缓存等机制配合使用，不能单独扛。

## 四、并发三问题：击穿、穿透、雪崩

这三个词经常被混用，其实机理完全不同，对应方案也不同。

### 4.1 缓存击穿（Breakdown）：热点 key 的过期瞬间

**机理**：某个热点 key（如爆款商品详情）恰好过期，恰好这一瞬间来了几千个并发请求，全部穿透到数据库，同一时刻执行同一条重建查询。数据库被一个 key 打爆。

**方案——重建锁（mutex / logical lock）**：

```
读请求发现缓存未命中:
  1. 尝试获取"重建锁"（SET NX EX，锁的 value 存当前线程标识）
  2. 拿到锁 → 去数据库查 → 写回缓存 → 释放锁
  3. 没拿到锁 → 短暂 sleep 后重试读缓存（或等待短暂超时后读缓存）
```

关键约束，踩过坑才记得住：

> **锁持有时间必须短于数据库查询超时时间。** 否则等待方在持有方查完库之前就超时了，锁形同虚设；或者持有方查询卡死，锁要等 EX 过期才释放，等待方全部超时雪崩。锁 TTL 建议 = P99 查询耗时的 2～3 倍，宁可锁提前过期再来一次击穿，也不能让锁长期不释放。

其他变体：也可以用"逻辑过期"方案——缓存 value 里塞一个过期时间戳，发现过期后由一个线程异步重建，其他线程先返回旧值。这个方案不会阻塞，代价是返回旧值的时间更长。对库存这种强一致的用重建锁，对展示类容忍旧值的可以用逻辑过期。

### 4.2 缓存穿透（Penetration）：查不存在的 key

**机理**：请求查一个库里根本不存在的数据（如恶意构造的 -1 号商品、随机 SKU），每次都缓存未命中、每次都落库。量大了就把数据库打穿。

**方案——空值缓存**：

- 库里查不到时，把"空"这个结果也缓存起来，设一个**短 TTL**（比如 30～60s）；
- 短 TTL 的原因是：这个 key 现在不存在，不代表下一秒也不会被创建。TTL 太长会导致"刚创建的数据查不到"；
- 布隆过滤器是更省内存的方案（在缓存前挡一道），但实现复杂且不支持删除，对参数化的查询 key 也不友好，当前没有采用。

### 4.3 缓存雪崩（Avalanche）：大量 key 同时过期

**机理**：大批 key 设置了相同或相近的 TTL，某一刻集中过期，重建请求洪峰打到数据库。常见于"凌晨批量预热了一批缓存"这种操作。

**方案——TTL 叠加随机偏移**：

```
实际 TTL = 基础 TTL + random(0, 基础 TTL 的 10%)
```

效果是把过期时间打散，5min 的 TTL 实际落在 5:00～5:30 之间，重建压力摊平到 30 秒里。另一个相关手段是**热点数据不过期 + 主动失效**，把"什么时候过期"的控制权从 TTL 手里夺回来，但代价是必须把主动失效做得非常可靠（回到第二节）。

### 4.4 三种问题的对比速查

| 问题 | 触发条件 | 打到数据库的是什么 | 核心手段 |
|---|---|---|---|
| 击穿 | 单个热点 key 过期瞬间 | 同一数据的并发重建查询 | 重建锁 / 逻辑过期 |
| 穿透 | 查不存在的数据 | 永远查不到的查询 | 空值缓存（短 TTL） |
| 雪崩 | 大量 key 同时过期 | 不同数据的重建洪峰 | TTL 加随机偏移 |

## 五、事件驱动失效：从轮询到推送

### 5.1 动机与收益

上面的"写库后删缓存"是写路径自己删自己的缓存，问题是：**一个数据的写路径可能有很多处**（后台管理端改、运营系统改、风控系统改、批处理改），任何一处漏了删缓存就是脏数据。事件驱动的思路是反过来：

```
任何系统修改数据 → 发变更事件（Kafka/MQ）→ 缓存服务订阅 → 主动删除对应 key
```

收益：

- **失效逻辑收敛到一处**：改数据的地方只需要发事件，不需要关心"这里改了要不要删缓存、删哪个 key"；
- **及时性**：相比定时轮询比对，事件是毫秒级的；
- **天然覆盖多写方**：批处理、对账脚本这些容易漏删的地方，统一走事件总线。

### 5.2 必须清醒认识：事件会丢、会延迟

事件是异步的，异步就意味着：

- 消息队列抖动时事件延迟几秒到几分钟；
- 消费失败重试耗尽后事件彻底丢失（除非有死信 + 人工介入）；
- 缓存服务重启期间的事件会积压，恢复后能否追上取决于保留策略。

**结论：事件驱动失效不能替代 TTL 兜底。** 事件的定位是"让正常路径更及时、更可靠"，TTL 的定位是"让异常路径有自愈上界"。两者是互补关系，任何"我们上了事件驱动所以可以不管 TTL"的想法都是危险的。当前事件链路（只对接到订单域变更事件）也配置了和重试队列类似的监控：消费延迟、积压量、死信数量。

## 六、已知缺口与演进方向

### 6.1 代际键 / 版本号机制（当前最大缺口）

当前方案的一个结构性问题：**删除失败后的补删窗口内，读请求会把旧值从库里读出来再回填进缓存**——等等，不对，补删期间库里已经是新值了。真正的问题是：

1. **回填旧值 vs 读到新值的竞争**：写库完成后、补删生效前，缓存里的旧值仍然在被读。更微妙的是，删除后、重建前的读会穿透到库拿到新值回填——但如果这时另一个延迟的旧事件/旧写操作的补删又到了，会把新值删掉，再下一次读又从库里读新值……在并发写场景下，"删"这个动作本身无法表达"删哪个版本"。
2. **无法区分"旧版本的旧值"和"新版本尚未生效"**：排查问题时，看到缓存和库不一致，无法知道是"失效没做"还是"写还没提交"。

**代际键的思路**：给缓存 key 加版本号。

```
key 不再是 product:12345
而是 product:12345:v17（v17 是数据的一个代际标识）
写路径：写库成功后，把代际标识推进到 v18（存在元数据里），旧 key 不再被读取
读路径：先查当前代际（v18），再读 product:12345:v18，查不到则重建
```

好处：

- **失效从"删除"变成"切换"**，旧版本 key 自然失效，不存在"删了又被回填旧值"的竞态——因为读方只认新代际；
- 老 key 设置短 TTL 自然过期回收，也不需要着急删；
- 排查问题时，对比代际号就能判断缓存和库差了几个版本。

代价：多一次代际查询（可以也缓存，变更时主动更新）、key 设计变复杂。TODO：等订单域方案稳定后推广到其他域。

### 6.2 失效粒度过粗

当前部分更新场景（比如只改了商品的运费模板）也会把整条目缓存删掉，导致下次读取全量重建。优化方向：

- 缓存结构拆细：把"展示频率高、变更频率低"的字段（品牌、类目）和"变更频繁"的字段（价格、库存）拆成独立 key，各自独立的 TTL 和失效事件；
- 或采用"字段级版本"：value 内部按字段带版本号，局部更新时只刷新对应字段。

粒度也不是越细越好——key 数量翻倍意味着击穿、雪崩的暴露面也翻倍，要和重建成本权衡。

### 6.3 其他待办

- 重试队列目前只覆盖了"删缓存失败"，**写库失败但缓存已被删**（如果有先删路径的遗留代码）导致的多余重建没有专门监控；
- 死信队列目前依赖人工处理，可以加自动告警 + 一键重放工具；
- 失效路径的端到端指标（写库完成 → 缓存删除完成 → 各节点可见新值）还没有打点，目前只能拿日志拼凑。

## 七、沉淀下来的原则清单

1. **失效而非更新**：删缓存，让读方重建，避免写写乱序。
2. **先写库后删缓存**：接受毫秒级窗口，换取删除失败时可重试、不残留脏数据。
3. **任何主动失效失败都必须有重试，重试队列必须有监控**——5 月事故用三天换来的教训。
4. **TTL 永远要设**，它是所有失效手段都失败后的自愈上界。
5. **TTL 按数据变化频率分级配置**，全库统一值是不负责任的偷懒。
6. **击穿用重建锁**（锁持有时间 < 数据库超时），**穿透用空值短 TTL**，**雪崩用 TTL 随机偏移**——三个问题三个方案，别混。
7. **事件驱动让失效更及时更收敛，但不替代 TTL**；事件链路本身也要监控。
8. **代际键是解决"删除竞态"的正道**，订单域验证后全量推广。
