# 消息投递语义笔记（订单事件链路）

> 背景：订单服务把"订单创建成功"等事件发到 MQ，下游报表、通知、风控都订阅。2026-09 的事故：MQ 集群抖动期间消费者端重试耗尽，一批"订单已支付"事件进了死信队列没人处理，支付通知延迟了 4 小时。事故复盘的结论和后台任务笔记（baseline-jobs）的教训同源：**投递语义理解错了，可靠性设计就是空中楼阁**。这篇笔记把三种投递语义、幂等消费、顺序保证理清楚。

---

## 一、三种投递语义与它们的代价

消息投递只有三种语义，没有第四种"完美的"：

- **at-most-once（最多一次）**：消息可能丢，绝不重复。实现简单（发完即忘），但丢消息在订单域不可接受。
- **at-least-once（至少一次）**：消息绝不丢，可能重复。实现需要确认+重试机制。**这是订单事件链路的当前选择**。
- **exactly-once（恰好一次）**：不丢不重。端到端的恰好一次在分布式系统里无法用纯消息机制实现——它必然是"at-least-once 投递 + 幂等消费"的组合。声称"我们实现了 exactly-once"而没有任何幂等机制的系统，要么在说谎，要么没想清楚。

订单域的选择是 **at-least-once + 消费者幂等**。理由在 jobs 笔记里已经沉淀过：投递会重复（网络超时后重发、消费者重启后重消费），所以消费必须幂等——这是分布式环境里"至少一次"语义的必然推论，不是可选项。

## 二、幂等消费的实现现状

消费端去重的实现（与 jobs 笔记的任务幂等同一个原则）：

- 每条消息带全局唯一 `message_id`（生产者生成，UUID）。
- 消费者收到消息后，先查去重表（message_id 是否已处理），处理过的直接 ACK 跳过。
- 去重记录与业务处理**同库同事务**：处理成功和去重记录一起提交，避免"业务成功了但去重没记上，重投又做一遍"。

去重表的 TTL 是 7 天——消息系统的重试窗口最长 72 小时，7 天覆盖了。**TTL 的选择要和消息系统的最大重投窗口匹配**，这是 9 月事故复盘后明确写下来的规则：去重窗口小于重投窗口，等于没有去重。

## 三、顺序保证：分区与单消费者

全局有序在 MQ 里做不到也不必要，要做的是**按业务键有序**：

- 同一订单的所有事件（创建→支付→发货）必须有序——消费者按 `order_id` 分区（哈希到同一个队列分片）。
- 同一分区内单消费者串行处理，天然有序。
- 跨订单的事件之间没有顺序要求。

代价要写清楚：单分区串行 = 热点订单会把整个分片拖慢（一个大订单的密集事件会阻塞同分区其他订单）。当前用"按订单哈希 + 分区内并发上限"折中，但热点问题没有根治。

## 四、死信与重试

消费者处理失败时的路径（9 月事故的核心教训）：

- **重试**：失败的消息进重试队列，指数退避重投。当前最多重投 3 次。
- **死信（DLQ）**：重试耗尽后进死信队列。当前死信队列**依赖人工处理**——9 月事故里死信积压 4 小时无人发现，就是死信没有监控。
- 事故后的两条新规则：① 死信队列深度、积压时长必须监控告警；② 死信处理要有"一键重放"工具，而不是手工捞消息。

这和缓存笔记（baseline-cache）里"重试队列本身要有监控"是同一条教训的第二次重演——**失败路径如果不被观测，它就等于不存在**。

## 五、事件与状态的一致性

事件携带的是"事实已发生"的通知，消费者拿它做决策前有个经典陷阱：**事件到达时，状态可能还没落库可见**。

订单域的顺序约定（与 jobs 笔记的"先状态落库再发事件"一致）：生产者先在数据库提交状态变更，事务提交**之后**才发事件。消费者收到事件后查库，一定能看到对应状态——因为状态先于事件。

反过来，如果消费者"收到事件就当状态已存在"而不回查，就会踩"事件先到、状态后到"的竞态。当前消费者规范是：**收到事件必回查状态库确认，以库为准**。

## 六、已知缺口

1. **死信处理自动化未实现**：监控告警有了，但"一键重放"还在开发。重放时的顺序保证（重放的消息和正常消息的先后）也没想清楚。
2. **exactly-once 的边界未文档化**：什么场景下"at-least-once + 幂等"等价于恰好一次、什么场景下不等价（如对外部系统的副作用调用）——没有成文边界。方向：把幂等消费覆盖不到的副作用（短信、第三方扣款）单独列为"补偿型"场景，走对账。
3. **热点分区的流量倾斜**：大订单密集事件阻塞同分区。方向：分区键再哈希一级（订单哈希 + 事件类型哈希），牺牲一点顺序性换均衡——但订单内事件顺序是硬约束，这个方向有争议，待讨论。

## 七、沉淀

- 只有三种投递语义，"恰好一次"= at-least-once + 幂等消费，没有别的实现路径。
- 去重表 TTL 必须覆盖消息系统的最大重投窗口，否则去重是纸糊的。
- 顺序保证按业务键分区做，全局有序既不必要也做不到。
- 死信和重试队列一样，是"必须被观测的失败路径"——9 月事故第二次证明了这一点。
- 事件是通知不是数据源：消费者必回查状态库，以库为准。
