# 结构化日志笔记（排障规范）

> 背景：一次线上排障花了 3 小时，根因是跨服务的调用链断了——request_id 在网关层就没传下去，下游服务的日志成了断头的线索，只能靠时间戳硬凑。2026-01 另一起事故性质不同但同样典型：日志里打出了完整用户手机号，被安全审计点名，之后逐服务排查手工脱敏的遗漏，扫出来的坑比预想的多。这两件事一个关乎**找不找得到问题**，一个关乎**日志本身安不安全**，促成了这套规范的成型。这篇笔记记录分类原则、字段与级别约定、脱敏和采样的实现方式，以及和分布式追踪打通的开放问题。

---

## 一、为什么先分三类：排障、审计、指标

规范的第一条不是"怎么打日志"，而是"什么算日志"。实践中三类需求经常被塞进同一个文件、同一个管道，然后互相伤害：

**排障日志**回答的问题是"请求处理过程中发生了什么"——服务收到了什么、调了谁、哪一步慢了、哪一步错了。特点是量大、细节多、只有出事那一刻才有人看，生命周期短。

**审计日志**回答的问题是"谁在什么时间对什么资源做了什么操作"——登录、改权限、导出数据。特点是量小、每一条都可能成为法律或合规证据，要求**不可篡改、长期留存、可检索**。把审计日志混进排障日志文件里，问题是双向的：排障日志按天滚动清理，会把审计证据一起清掉；反过来审计字段混进高频排障日志，又放大了敏感信息的面。

**指标事件**看起来最不像日志——QPS、延迟分位数、缓存命中率，本质上是可聚合的数值。它们走进文本日志文件是个反模式：聚合要靠日志系统事后解析文本再数数，链路长、延迟高、还容易和真正的排障日志抢索引资源。正确归宿是指标系统（时序数据库），打的时候就以数值形式进，不走文本。

三类数据分三条通道：排障日志进日志管道（结构化 JSON → 采集 → 日志系统），审计日志单独通道落库（带完整性保护），指标直接进指标系统。这个划分看起来是运维层面的洁癖，实际收益在出事时才显形：排障时不用在审计记录里捞排障线索，安全审计时不用在海量排障日志里翻敏感操作，指标告警也不会因为日志管道堵塞而失灵。**分类的代价是三个管道，不分类的代价是每一次使用场景都被其他场景污染。**

## 二、字段规范

### 2.1 基础字段：每条日志的"身份证"

每条日志必须携带四个字段：`timestamp`、`level`、`service`、`request_id`。前三个的意义自明，重点是 `request_id`——它是整篇笔记的主角，也是 3 小时排障事故的直接解药。

### 2.2 request_id：在入口生成，随链传递

约定是：`request_id` 在请求入口（网关或第一个接收请求的服务）生成，之后**随调用链向下游传递**——HTTP 调用走请求头，消息队列走消息元数据，下游服务接到后不重新生成，而是沿用同一个 id，同时把它注入自己的日志上下文。

这样跨服务排查就退化成一条查询：按 `request_id` 过滤，所有服务的日志按时间排好，完整调用路径原地还原。听起来理所当然，但断裂的方式五花八门：网关没透传、下游框架默认过滤未知请求头、MQ 消费时没从消息属性里取、异步线程池切换时上下文没跟着走。规范里专门强调"沿用同一个 id"而不是"各自生成再关联"，是因为关联方案（比如每服务一个 id 再维护映射表）在压力下必然退化成对不上的两套 id。**透传方案的正确性依赖每一跳都不偷懒，所以每一跳都要写进框架层而不是交给业务代码自觉。**

异步场景的上下文传递值得单独提一句：主线程把 request_id 交给线程池任务时，要用上下文包装（MDC 之类的机制显式传递），不能依赖 ThreadLocal 自动继承——线程池的线程是被复用的，上一个任务的上下文会泄漏到下一个任务，造成"张三的请求日志里混着李四的 request_id"这种极难察觉的错乱。

### 2.3 业务字段：命名稳定是隐形契约

业务字段用 snake_case。比风格更重要的是**字段名要稳定**——这条规范背后有一次惨痛的教训：某次重构把 `userId` 改成 `user_id`，当时觉得只是风格统一，上线后才发现历史日志查询全废了——按旧字段名建的所有仪表盘、告警规则、排查惯用的查询语句全部失效，而日志系统里新旧字段并存了留存期整整 30 天，查询结果时有时无。

理解这件事的角度是：**字段名不是代码里的变量名，是写入持久化存储的 schema**。改数据库列名要做迁移，改日志字段名同样应该有迁移——双写新旧字段一个留存期、查询切到新字段、再停旧字段。规范层面能做到的是写入侧冻结：字段名一旦上线，视为不可变的对外契约，真要改，走双写迁移流程。查询侧的人也要有这个意识：查询语句里的字段名是历史快照，跨时间范围查询时要确认字段在那个时间是否存在。

## 三、级别约定：ERROR 稀缺化

级别系统的腐化有一个固定剧本：ERROR 太多 → 告警疲劳 → 真 ERROR 被淹没 → 有人把真 ERROR 升级成 PAGER → 更疲劳。破局的办法是从定义上让 ERROR 稀缺。

**ERROR 只用于需要人立即介入的故障。** 判断标准不是"这个调用失败了"，而是"这件事如果发生在凌晨三点，值不值得把人叫起来"。下游超时但本地有降级——INFO，记一笔降级发生了。某个非核心路径的校验失败——WARN。整个请求处理不下去了、数据可能不一致了——这才是 ERROR。

**同一条错误沿调用链重复打 ERROR 是最常见的滥用。** 一个底层数据库抖动，可能被五六层服务各自捕获、各自打 ERROR、各自触发告警，值班的人收到一片告警雨，真正有用的信息（根因在最底层）反而埋在重复噪音里。约定是：**错误只在最外层边界（通常是请求处理入口的兜底 catch）打一次 ERROR**，内层捕获到时打 DEBUG 带完整上下文，外层 ERROR 里的堆栈和消息会带上根因信息，排查从外层进入、向内下钻。一条错误一条 ERROR，告警量和可处理性立刻回到正常水平。

**INFO 是请求级关键节点的流水**：收到请求、调用下游、返回结果、关键分支走向。一条请求的 INFO 不超过十条——超过十条说明在打 DEBUG 级别的内容却占着 INFO 的成本，也说明这个服务的请求处理步骤多到该拆分。INFO 的价值在于"不看 DEBUG 也能还原请求的主干"，它应该像路标一样稀疏而明确。

**DEBUG 装下完整上下文**，生产默认关闭。默认关闭意味着 DEBUG 日志是"随时可以打开的时间机器"——排障时给特定服务、特定用户、特定接口临时开 DEBUG，而不是平时把所有细节都付了采集和存储的钱。这里有个配套要求容易漏：DEBUG 开关要支持运行时动态调整（按服务、按级别），不支持动态调整的开 DEBUG 就得发版，时间机器就变成了摆设。

## 四、脱敏：框架层做，不靠手工

2026-01 事故的教训概括起来是一句话：**手工脱敏必然有遗漏。** 当时一个服务在打印请求参数时手工掩码了手机号字段，评审和测试都过了，但三个盲区没人看见：某个嵌套对象里还有一个联系方式字段没掩、异常堆栈里抛出的原始请求体带着完整手机号、后来加的新字段从来没人想起要脱敏。安全审计点名之后逐服务排查，几乎每个服务都有类似的盲区——不是人马虎，是这种模式根本兜不住。

规范改成了：**脱敏下沉到日志框架层，靠字段名识别**——`password`、`token`、`authorization`、`phone`、`id_card` 等敏感字段名命中规则库，框架在序列化输出前统一掩码，业务代码不允许、也不需要手工脱敏。这个转变的核心逻辑是：手工脱敏把正确性寄托在每个开发者每次打印时都记得，框架脱敏把正确性寄托在一个集中维护的规则库上——前者是概率正确，后者是确定正确，而且规则库可以随合规要求迭代升级，一次改动全服务生效。

配套的规则：

- 密码、token、身份证、完整手机号**默认不落日志**。不是"打但脱敏"，是这条日志根本就不该带这些字段——能不打就不打，必须打引用就脱敏后打，"需要排查问题时用完整手机号查"不是理由，排查用内部 ID 关联，不从日志反查敏感明文。
- 规则库要覆盖**值模式**兜底，不能只认字段名。字段名识别有一个结构性盲区：字段名不规范的（`mobile_no`、`contact`）会漏。值模式兜底（11 位 1 开头的数字序列疑似手机号、18 位身份证校验位合法的疑似身份证）能兜住"字段名没进规则库"的漏网之鱼。正则扫值的成本可以接受，漏一次的代价是审计事故。
- 异常堆栈要过同一套脱敏管道。事故里的堆栈明文就是走的这个洞——日志框架序列化堆栈消息时，同样应用字段规则和值模式，而不是把 `e.getMessage()` 原样写出去。

这套机制的诚实边界也写明：字段名 + 值模式是启发式，不是形式化验证，新型敏感数据类型（比如银行卡号）进规则库之前存在一个窗口。所以审计定期的日志抽检不能省——框架层脱敏把"每个服务每次打印"的正确性问题降级成"规则库 + 定期抽检"的维护性问题，这是它能达到的最好效果，不是终点。

## 五、采样：按请求采，不在半路采

采样上走过的弯路是"按日志条数采样"——每天日志量太大，直接随机保留 1% 的日志行。后果是排障时发现调用链是碎的：请求的主干留下了，中间某三步恰好被采掉，关键那次下游调用恰好没留，一条断成几截的链比没有链更让人恼火。

规范改成了**按请求采样**：采样决策在请求入口做出（这个请求留还是不留），决策随 request_id 一起沿调用链传递，下游服务沿用同一个决策。效果是同一条请求的所有日志要么全留、要么全不留——留下来的 1% 是完整的 1%，排障时这 1% 的链是通的。

当前的参数：正常流量采样率 1%，ERROR 全量保留。注意这两个规则的交集语义：ERROR 全量优先于采样丢弃——一个被判为"不留"的请求如果最终出了 ERROR，它的日志要全部捞回来。这要求采样决策是"软"的（日志先落本地缓冲或短期缓存，决策回收后再真正丢弃），而不是在写入时直接不发。ERROR 全量保留的意义在于：排障时最需要的恰恰是那些失败请求的完整上下文，如果失败请求也可能被采样掉，1% 的留存率乘以低失败率，剩下的失败样本就寥寥无几了。

采样率 1% 本身不是信仰，是成本和覆盖率的平衡：按当前流量，1% 已足够覆盖告警触发的排查需求，同时存储成本可控。大促扩到多少、日常能否放宽，看存储水位动态调，规范只固化"按请求采、入口决策、ERROR 全量"这三个结构性原则。

## 六、已知缺口：追踪与时钟

**缺口一：日志和分布式追踪没有打通。** 当前的 request_id 是应用层自造的 ID，服务于日志之间的串联，但和追踪系统的 span 上下文完全无关。实际排障时的撕裂感很明显：日志按 request_id 串起来了，但想进一步看这条请求的时序分解（每个 span 的耗时、并发关系）时，得拿着时间戳去追踪系统里人肉捞对应的 trace，两个系统之间的桥全靠手和眼。

TODO 里悬着一个问题：等追踪系统接入后，**request_id 要不要直接换成 trace_id？** 目前的倾向是两者职责不同、不要合并，理由记录如下：trace_id 解决的是"这次分布式调用的拓扑还原"，由追踪系统生成、跟着 span 走、跨越的边界（包括异步消息、定时任务）比日志关心的更宽；request_id 解决的是"应用日志的串联"，生命周期跟着请求处理走。合并成 trace_id 的好处是少一个字段、日志和追踪天然对齐，但代价是日志体系对追踪系统的可用性产生硬依赖——追踪 collector 挂了、trace_id 注入失败，日志串联立刻退化，这个耦合不划算。更现实的方案是**两者并存并在入口对齐**：入口同时生成/接收两者，日志里两个字段都带（`trace_id` 优先从传入的追踪上下文中取，没有则留空），查询系统支持按任一跳转。等于让 request_id 做稳定的老本行，trace_id 做日志到追踪的跳板，职责清晰，单点故障也隔开了。

**缺口二：跨服务时钟未统一。** 按时间排序还原调用链依赖所有服务的 `timestamp` 可比，但服务间时钟偏差（NTP 同步滞后、容器漂移）会让排序错乱——上游调用下游的日志时间戳反而更早几百毫秒，链条在时间上自相矛盾，只能靠 request_id 强扭回正确的顺序。根治方案是所有服务统一时钟源（NTP 加严、或日志采集侧统一用采集时间 + 原始时间双时间戳），当前靠 request_id 兜底排序，属"能用但脆"的状态。

## 七、沉淀

排障三小时事故和脱敏审计事故，一个花在了**断掉的链**上，一个花在了**不该出现的内容**上，恰好是日志体系的两个基本面：可用性和合规性。这两条规范的本质可以归纳成两句话——**串联靠机制不靠自觉**（request_id 透传、采样决策传递、脱敏下沉框架层，全都是在把"每个人每次都做对"换成"框架保证做对"），以及**日志是写入存储的 schema，不是随手打印的字符串**（字段名稳定性、级别稀缺性、分类分通道，都是把这个事实当真之后的自然推论）。
