# 分布式锁笔记（Redis 实现，订单服务）

> 背景：订单服务多副本部署，同一个订单可能被多个副本同时处理——对账、扣款、状态推进这些操作如果不互斥，轻则重复扣款，重则资金错误。引入了基于 Redis 的分布式锁来做同一订单的互斥。2026-04 的事故给这套机制敲了警钟：一个 worker 因 GC 停顿了 40 秒，锁过期被另一个副本抢走，两个副本同时处理同一订单，旧 worker 恢复后继续写，产生了双扣。这篇笔记梳理当前实现、那次事故暴露的问题，以及续期失败后"取消还是继续"这个悬而未决的争论。

---

## 一、锁到底在解决什么问题

先把问题的边界划清楚，后面所有的设计讨论才不会跑偏。

订单服务多副本之后，"同一订单被并发处理"从理论风险变成日常风险：两个副本同时抢到同一个订单任务、用户重复点击触发两路处理、重试流量和正常流量撞上。这类问题的共同点是——**单个操作在单进程内是安全的，多个进程交错执行就出错**。分布式锁要解决的正是这个：把并发交错强行排成串行，让任意时刻只有一个持有者在处理这个订单。

但要在一开始就声明：锁只承诺**互斥**，不承诺**正确**。锁能保证两个进程不会同时持有同一把锁，但不能保证持有者内部不出错、不能替代幂等、不能兜底下游副作用。这是贯穿全篇的基调，4 月事故本质上就是一次对"锁承诺边界"的误读。这个边界放到后面第六节展开，先记下。

## 二、获取与释放

### 2.1 获取：一条原子命令

```
SET lock:order:{order_id} {token} NX PX {ttl}
```

四个要素缺一不可：

- **NX**（not exist）：只有 key 不存在时才设置成功，设置成功即视为获取成功。这是互斥语义的载体——多个客户端同时执行，Redis 单线程模型保证只有一个 SET 能成功。
- **PX {ttl}**：设置过期时间，单位毫秒。**租约必须和获取是同一个原子操作**。如果拆成 `SETNX` + `EXPIRE` 两条命令，中间客户端崩溃，key 就成了永久键——这正是"锁必须有租约"原则的实现方式：TTL 和锁的写入绑在同一条命令里，不存在"忘了设过期时间"的窗口。
- **token**：每次获取时生成的随机值。它的存在意义在释放环节才完全显现，见下。

重试策略：获取失败说明锁被别人持有，sleep 一个随机短间隔后重试，上限三次。随机间隔是为了避免多个等待方在锁释放的瞬间齐刷刷重试，形成重试风暴把 Redis 打抖。

### 2.2 释放：为什么必须 Lua 脚本

释放锁看起来是"删 key"一个动作，直接 `DEL` 会引发一个经典的竞态：

```
1. 进程 A 持有锁，任务执行时间超过 TTL，锁自动过期
2. 进程 B 趁机获取锁，开始处理同一订单
3. 进程 A 执行完，DEL 掉锁——删掉的其实是 B 的锁
4. 进程 C 又获取锁……互斥从此形同虚设
```

问题在于"判断这把锁是不是我的"和"删除"是两个独立操作，中间任何时刻锁都可能易主。解法是把判断和删除合成一个原子操作，用 Lua 脚本在 Redis 服务端一次执行完：

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

token 在这里起作用：只有 value 和自己持有的随机 token 一致才删，不一致说明锁已经是别人的，默默退出。这也解释了 token 为什么必须是**每次获取独立生成**的随机值，而不是进程号、线程号这类标识——同一进程可能先丢失锁、再（重试）重新获取，进程号不变而锁的实际持有者已经换过几轮；随机 token 则让"我是谁"这个问题精确到"哪一次获取"，杜绝了同标识误删的空间。

顺带一提：释放成功返回 1、token 不匹配返回 0，这个返回值值得记录到日志里。释放时发现 token 不匹配，说明"我执行期间锁已经易主"，本身就是个危险信号，应当告警而不是默默吞掉。

## 三、租约与续期

### 3.1 锁必须有租约

不设 TTL 的锁意味着：持有者崩溃（或者拿到锁之后代码路径异常退出），锁永远滞留，同一订单的后续处理全部被拒——从"防止并发"变成"禁止处理"，可用性灾难。租约让锁有了自愈能力：**持有者崩溃，租约到期自动释放，其他人接管**。代价是持有者必须保证"我的活干得完"或者"我会续租"，这把锁从"一个布尔状态"变成了一个需要持续维护的契约。

### 3.2 TTL 取值

TTL 要覆盖正常任务的执行时间，当前的经验值是**任务 p95 耗时的两到三倍**。取 p95 而不是均值或 p50，是因为锁保护的恰恰是最慢的那部分任务——均值漂亮的系统，长尾任务照样把锁拖到过期。三倍余量是对 GC 停顿、网络抖动、下游抖动的折中：余量太小，正常波动就导致频繁过期易主；余量太大，持有者真崩溃时接管延迟被拖长。

### 3.3 续期机制

任务执行时间可能超过 TTL（比如对账任务碰上大促数据量），允许持有者按固定周期续期：每过一个远小于 TTL 的间隔（如 TTL 的 1/3），对锁重新设置 TTL。两条纪律：

- **续期请求必须带 token 校验**——用和释放相同的 Lua 逻辑，"token 匹配才续期"。否则一个已经失去锁的进程（比如 GC 停顿醒来）可以给自己"续"一把已经属于别人的锁，互斥再次失效。token 校验是续期和释放共同的守门员。
- **续期失败必须按"已失去锁"处理，而不是按"Redis 抖了一下"处理。** 这一点单独成段，因为它正是 4 月事故的核心教训，也是当前最有争议的开放问题（第七节展开）。

### 3.4 关键事实：过期即丧失资格

把这条写成加粗，因为它是整个锁机制里最反直觉、也最重要的一条：

> **只要进程持有未过期的锁，就可以安全地进行独占操作。反过来，锁到期而未续期成功时，进程必须立即停止操作——即使任务已经执行了一半。过期意味着可能有新持有者已经接管，继续操作就是和新持有者并发。**

"执行了一半"的沉没成本不能成为继续的理由。此时任务结果的正确做法是**标记为可疑**，交给后续的核验/幂等/对账流程去裁决，而不是提交，也不是直接丢弃。提交是把风险转嫁给资金正确性，丢弃是把成本转嫁给自己——两个方向都比"标记可疑"差。

## 四、GC 停顿与 fencing：4 月事故复盘

事故经过：一个 worker 因 GC 停顿 40 秒，超过了锁的 TTL。锁过期，另一个副本正常获取并开始处理同一订单。40 秒后旧 worker 恢复，**它对这一切毫无感知**——它的本地状态里"我还持有锁"，token 还是原来那个，于是继续执行扣款，双扣发生。

复盘这个事故，要害在于：**锁的过期判定依赖时间流逝，而 GC 停顿时进程内的一切——包括它的自检逻辑——都冻结了。** 进程醒来后，"我的锁过期了吗"这个问题它没有可靠的手段回答：问 Redis，Redis 会告诉它"锁现在是别人的"，这已经晚了；看本地时钟，40 秒已经过去了，但它无法知道过期和被抢占具体发生在它暂停期间的哪一刻，也无法确定抢占者此刻是否已经完成。token 机制保护的是"不误删别人的锁"，保护不了"停顿醒来的进程自己继续写"。

这类问题的系统性解法是 **fencing token（栅栏令牌）**：锁服务每次发放锁时返回一个单调递增的序号（epoch），持有者执行每次写操作时把这个序号带给共享资源（比如数据库），资源方只接受比已见序号更大的写入：

```
worker A 获取锁 → 得到 epoch 41 → 停顿
锁过期，worker B 获取锁 → 得到 epoch 42 → 开始处理
worker A 醒来，带着 epoch 41 发起写库
数据库：已见最大 epoch 是 42，41 < 42，拒绝
```

fencing 的本质是把互斥判断从"时间维度的 lease"搬到"序号维度的比较"——时间会被暂停，单调递增的序号不会说谎。对订单库来说，落地方式并不复杂：锁用 `INCR` 产生 epoch，扣款 UPDATE 语句的 WHERE 条件里带上 `AND lock_epoch < 41` 之类的比较，相当于把乐观锁和分布式锁焊在一起。**代价是共享资源必须参与协议**——纯 Redis 锁给不了这个保证，这是 Redis 锁方案诚实的边界（见第六节）。

当前状态：fencing 尚未实现，属于已知缺口里优先级最高的一项。在落地之前，缓解措施是尽量缩短锁内临界区（把网络调用、重 IO 挪出临界区）、TTL 留足余量、以及依赖第七节讨论的"续期失败即停"纪律来缩小危险窗口——这些都只是降低概率，不是根除。

## 五、获取超时：不无限等待

获取锁失败时的行为必须有界。当前实现：排队等待，等待超过上限后返回"获取失败"，把降级决策交还给调用方（跳过本次处理等下一轮、走只读路径、或者报警人工介入），**不无限阻塞**。

无限阻塞的害处在于，锁迟迟拿不到通常意味着系统出了异常（持有者崩溃但租约很长、或者持有者死循环每到期就续上），这时把请求线程无限挂起，等于把局部的锁问题扩散成全局的线程池耗尽。有界的等待 + 明确的失败返回，让锁问题停留在锁问题。

当前参数：获取超时取租约 TTL 的一半，重试上限三次。**这两个数字没有理论最优解**，是按当前业务的互斥窗口拍的：业务上"同一个订单晚一个 TTL 周期再处理"可以接受，所以等待上限压在半个 TTL；重试三次是抖动容忍度和 Redis 压力之间的折中。换业务、换流量特征都要重新评估，直接抄数字没有意义。

## 六、锁不解决什么：边界声明

两条容易混淆的陈述，差别细微但重要：

**"锁保证同一时刻只有一个进程持有锁"——这是锁真实提供的。**
**"锁保证同一时刻只有一个进程在操作共享资源"——锁不提供这个保证。**

两者的缝隙里站着 GC 停顿、网络分区、时钟漂移这些不可控因素。锁的排他性建立在"过期时间到了持有者就真的不能操作"这个约定上，而这个约定靠进程自觉——自觉在停顿、分区面前会失效。所以：

**第一，锁解决互斥，不解决副作用。** 持有锁期间的操作仍可能因进程假死、分区恢复后的重试等原因重复执行，这些属于幂等设计的范畴。锁把并发从"任意交错"压缩成"极小的竞态窗口"，幂等负责把这个窗口里的重复执行变得无害。两个机制各司其职，指望锁兜住一切幂等问题，或者指望幂等所以不用锁，都是错的。

**第二，锁内临界区要短。** 锁住的代码越长，撞上停顿、抖动、过期的概率越高，锁内还阻塞着其他等待方。临界区里只放真正需要互斥的那段——读-改-写共享状态的最小片段。网络调用、发消息、写日志这些挪到锁外。

**第三，资金类操作，锁 + 幂等 + 对账是三层缺一不可。** 锁负责串行，幂等负责重复无害，对账负责兜住前两者的残余错误。4 月事故中双扣最终是靠对账发现的——这个顺序说明前两层都有洞，也说明第三层确实是最后的防线，要好好维护。

## 七、续期失败后：取消还是继续？

这是当前争论最久、也最想定下统一规则的问题。背景是 3.4 的关键事实：续期失败必须按"已失去锁"处理。但"停止操作"具体怎么停，有两种倾向：

**立即取消派**认为：续期失败 → 立即终止任务，已做的工作作废重来。理由是简单、统一、没有歧义——任何情况下都不给"可疑写入"留机会。

**完成派**质疑：任务执行到 90%，中间结果全在内存里，这时候取消，重跑一遍的成本可能远高于"把它做完再核验"的成本；而且取消本身也不是免费的——部分完成的副作用可能已经发生，作废重来未必干净。

两边的论据都成立，说明"一刀切"可能本身就是错的，问题应该换个切法。**按副作用的性质切，而不是按完成度切**：

- **可逆操作**（事务内写库、可回滚的状态变更）：续期失败后，把当前这个原子单元做完、提交或回滚干净，然后停止，不再发起新的原子单元。已完成的变更走核验。
- **不可逆操作**（扣款、对外发消息、调用第三方）：续期失败后，在下一个不可逆动作**之前**立即停止，没有任何讨论空间。已经发生的不可逆动作，立刻进入对账流程人工或自动核销。

落到统一规则上，目前的草案是：

> **续期失败 = 转入"只收尾、不新增"模式。** 完成当前原子单元，保存中间状态，任务标记为 pending-verify，交由幂等校验或对账流程裁决。任何新的副作用动作发起前，必须重新确认仍持有锁；确认失败即停止。不立即杀任务，也不允许带着"可能已易主"的状态继续产生副作用。

这条规则还顺带统一了一个之前各服务自行其是的灰色地带：续期失败后的降级路径此前没有约定，有的服务继续跑完，有的服务直接抛异常，行为全凭当时写代码的人的心情。有了上面的规则，"继续"有了明确的边界（只收尾不新增），"停止"也有了明确的姿态（标记可疑而非丢弃）。

另外值得记一笔的体会：争论"90% 时取消亏不亏"，往往说明任务本身不可断点续传——可断点的任务取消起来毫无心理负担。所以比规则更重要的方向性建议是：**长任务尽量做成可 checkpoint 的**，让"取消"从"前功尽弃"变成"下次从断点继续"，这个问题会自然消解大半。规则是止血，checkpoint 是治本。

## 八、已知缺口汇总

| 缺口 | 现状 | 优先级 |
|---|---|---|
| **无 fencing token / epoch** | GC 停顿醒来的进程无验证手段，4 月事故根因；落地需订单库配合（UPDATE 带 epoch 比较） | 最高 |
| 续期失败降级路径无统一约定 | 各服务自行处理；第七节有规则草案，待评审固化 | 高 |
| 释放时 token 不匹配未告警 | 静默返回 0，丢失"执行期间锁已易主"的信号 | 中 |
| 锁内临界区长度无约束 | 靠 code review 把关，未做强制检查（如锁内禁止 RPC 的静态检查） | 中 |

结尾沉淀的原则，和开篇呼应：**分布式锁是一份有租约的契约，不是一把物理锁。** 物理锁断了就是断了，租约锁过期了持有者却可能浑然不觉——所有围绕 token、fencing、续期纪律的设计，本质上都是在弥补"锁的释放不依赖持有者的知情"这个固有缺陷。理解了这一点，4 月事故里每个环节为什么那样设计，就都说得通了。
