
# 后台任务生命周期笔记

> 背景：报表生成、数据回填这类长任务从 Web 进程挪到了后台 worker。系统跑起来之后发现，长任务本身不容易写错，**任务的"生命周期管理"才是一地坑的地方**——任务怎么入队、怎么被领取、worker 挂了任务去哪、事件发丢了谁管，每一个环节出问题表现形式都是"任务卡住"，但根因完全不同。2026-03 的事故（发布时全量重启 worker，重启瞬间掉了 12 个 running 任务，状态一直卡着，最后人工逐个重放）就是典型的生命周期问题。这篇笔记把当前实现和踩过的坑整理一遍。

---

## 一、先把状态机想清楚

后台任务系统的一切设计都从状态机出发。当前定义了四个状态：

```
queued（已入队等待领取）→ running（被 worker 领取执行中）→ succeeded / failed（终态）
```

看起来朴素，但有两条原则是整个系统的地基，都是出过一次事之后才立下来的。

**第一，状态转换必须持久化，不能只存在 worker 内存里。** 这听起来是句废话，但早期实现里 worker 领取任务后只是把任务对象放在本地内存队列里跑，数据库里的状态还是 queued。后来 worker 一重启，这堆任务的踪迹彻底消失——不是 failed，不是 cancelled，是**没人知道它们存在过**。排查这类问题的痛苦在于日志还在、任务记录还在，一切"看起来正常"，只有业务方三天后问"我的报表呢"才发现不对。教训就是：worker 内存里允许有缓存态，但任何**状态迁移的决策点**都必须落在持久化存储里，内存里的东西随时可能蒸发。

**第二，状态持久化要和业务数据的写入在同一个事务里。** 任务的终态标记和业务结果是两个事实："报表生成成功"和"任务被标记为 succeeded"，这两个事实必须同时成立或同时不成立。如果分开提交，中间 worker 崩溃，就会出现"报表其实生成了但任务显示失败，被重放又生成一份"或者反过来"任务显示成功但报表是残缺的"。把两个写入放进同一个事务，让数据库的 ACID 替我们保证这个原子性——这是整个系统里少数能"免费"拿到的可靠性，不用白不用。

## 二、领取：先标记，后执行

worker 怎么从队列里拿任务，是丢不丢任务的关键。

现在的做法是：worker 从队列取出任务后，**先以原子方式把状态从 queued 改成 running，同时记录 worker 标识和领取时间，更新成功之后才真正开始执行业务逻辑**。

这里有个微妙的点值得展开：为什么是"先标记"而不是"先执行完再顺手标记"？反过来的流程是——取任务、执行、执行完把状态改成 succeeded。如果 worker 在"取任务"之后、"标记完成"之前的任意时刻崩溃，这个任务就处于"实际被执行了一部分、但系统里看起来还是 queued"的状态。它会被下一个 worker 重新领取、重新执行。这本身靠幂等可以兜住（见下节），但问题在于**你不知道它上次执行到了哪一步**。而先标记 running 再执行，崩溃后任务的状态清清楚楚是 running——它确实被领取过、确实执行中断了，系统对"任务去哪了"有明确的认知，剩下的问题只是"怎么恢复它"，而不是"它到底发生了什么"。

从"去向不明"降级成"卡在 running 待恢复"，是可靠性上的一大步。

原子更新还顺带解决了多 worker 并发扫描的争抢。多个 worker 同时扫到同一个 queued 任务时，`UPDATE ... WHERE status = 'queued'` 这种带条件更新的语句天然只有一个能成功，成功方获得任务，失败方继续扫下一个，不需要额外的分布式锁。

领取时间记录下来也有用武之地——它既是超时判断的依据（见下），也是崩溃恢复时判断"这个 running 任务死了多久"的依据。

## 三、幂等：任务一定会被执行多次

设计上必须接受一个事实：**任何任务都可能被执行一次以上**。触发原因五花八门——执行超时后的重试、worker 崩溃后的重新领取、人工重放，甚至将来加了任务依赖功能之后的级联重跑。指望"调度足够小心所以不会重复"是不现实的，正确姿势是让重复执行无害。

当前的实现是给每个任务分配全局唯一 ID，业务处理逻辑以这个 ID 去做去重。比如回填任务，处理前先查"这个 task_id 的处理记录是否已存在"，存在则跳过核心副作用。

去重状态必须落在持久化存储里。这一点单独强调，是因为早期版本图省事用了进程内的去重表（一个内存 Set），当时测试单进程重试是好用的。但人工重放完全可能发生在**进程重启之后**——内存里的去重记录早就没了，同一条任务被实打实执行了两遍，下游数据出现重复。所以"幂等键的存储介质"和"重放可能发生的时机"必须匹配：重放能跨进程、跨重启，去重就必须跨进程、跨重启。

另外一个体会是：幂等判断最好做成业务侧的一个显式步骤，而不是藏在框架里偷偷生效。显式的好处是代码评审时能看见"这里重复执行会发生什么"，而不是默认框架会兜住。

## 四、超时与取消

**超时**是任务维度的保险丝。每个任务带超时时间（按任务类型配置），执行超过时限，worker 中断执行并把任务标记为 failed，错误信息连同堆栈快照写进任务记录。超时的存在意义不只是保护 worker 资源，更是为了不让"卡住的任务"伪装成"还在正常跑的任务"——没有超时的系统里，一个死循环的任务会一直占着 running 状态，监控上一切正常，直到下游业务炸了你才发现。超时把这类问题变成明确的 failed，可见、可告警、可重放。

**取消则是另一回事，它是协作式的。** 取消的实现方式是：外部（管理接口或上游系统）给任务打上取消标记，worker 在执行业务逻辑时设置若干个检查点，执行到检查点时看一眼标记，发现被取消就干净地退出并标记终态。

为什么不用强杀？因为强杀的本质是 worker 在**任意一个中间状态**被断电，而很多业务逻辑的中间状态是危险的——比如回填任务写了一半数据表、报表任务生成了一半文件。检查点之间的代码是不可分割的最小单元，强杀进去数据就停在半途，留下一个写了一半的中间态，比"没执行"更难收拾。所以宁可让取消有一点延迟（最坏情况延迟 = 两个检查点之间的耗时），也要保证取消发生时业务数据处于完整状态。取消延迟这个特性要写进对外的接口文档里，不然调用方会以为取消是即时的。

有个遗留问题：取消后的任务算 failed 还是单独的 cancelled 终态？当前统一按 failed 处理，副作用是取消的任务混在真正失败的任务里，告警和统计时会互相干扰——排查 3 月事故时就人工从 failed 列表里把"其实是被取消的"挑出来过。TODO 里记着考虑拆开成独立终态，顺便给超时失败也单独一类，三类失败（超时 / 主动取消 / 执行异常）的可恢复性和处理动作完全不同，混在一起统计意义不大。

## 五、完成事件：顺序不能反

任务到达终态后需要通知下游——比如"回填完成"触发下游统计任务、"报表完成"通知用户下载。事件的发布有一个非常容易被写反的顺序问题：

**必须先状态落库，再发布事件。** 反过来的话（先发事件再落库），事件消费者收到通知后去查任务状态，查到的是旧状态——running 甚至 queued，消费者按"任务还没完成"处理，或者干脆查不到数据产生空指针。这种竞态窗口平时概率极低，压测不出来，但流量一大必现，且出现时毫无规律，极难排查。

所以顺序是：事务提交 → 发布事件。事件发布失败不能阻塞主流程——任务本身已经成功，不能因为它下游没人知道就回滚，那是本末倒置。失败的事件进补发队列，由后台任务定期扫描补发。这带来一个必然的语义：**事件至少投递一次**（at-least-once），也就意味着消费者可能收到同一个完成事件两次。应对方式和任务幂等是同一个原则——消费者按任务 ID 去重，容忍重复，保证处理幂等。整个系统里"幂等"这个词出现了三次（任务执行、事件消费、人工重放），不是巧合，而是分布式环境里"至少一次"语义的必然推论：投递会重复，所以消费必须幂等，这是所有异步链路逃不掉的税。

## 六、已知缺口：worker 崩溃后的 running 任务

这是当前最大的洞，3 月事故的直接根因。

流程是这样的：worker 领取任务后任务进入 running，worker 正常跑完会把任务推到终态。但**worker 进程突然死掉**（发布重启、OOM、机器故障）时，它手里的 running 任务没有任何机制被接管——下一个 worker 扫描队列时只认 queued，不会去看 running；任务不会超时（因为超时判断也是 worker 自己做的，worker 都死了谁来判断）；于是这些任务就永远卡在 running，直到有人发现报表迟迟没生成，翻任务列表看到一串 running 但实际已经死透的任务。

3 月事故的完整时间线：发布系统滚动重启 worker，重启瞬间有 12 个任务正在 running。任务没丢（"先标记后执行"保证了状态清晰），但没有恢复机制，12 个任务原地卡死，业务方等了两天没等到报表，人工逐个检查后重放才恢复。

根因用一句话概括：**running 状态是"租约"语义，但我们只把它当成了"状态"存储，没有租约的续期与回收机制。**

正确的方向是租约（lease）：

```
worker 领取任务 → 获得租约，默认比如 30 秒
worker 执行期间定期续租（心跳），证明"我还活着，还在处理"
worker 崩溃 → 心跳停止 → 租约到期 → 其他 worker（或专门的恢复扫描器）发现租约过期的 running 任务 → 回收，重置为 queued 重新调度
```

租约机制设计上有几个要点。续租间隔要显著小于租约时长（比如 10 秒续一次、租约 30 秒），否则续租请求本身的抖动会造成误判；回收扫描的频率决定恢复时效，30 秒扫一次，最坏情况任务卡死 30 秒就被重新拉起，比"人工发现"快了三个数量级；回收时要小心"假死"——worker 没死只是网络分区心跳断了，这时任务可能被两个 worker 同时执行，**又绕回了幂等**，去重逻辑必须兜住这种情况。

当前在租约没有实现之前，兜底的替代方案是定时任务扫描"running 且领取时间超过阈值"的任务，把它们标记出来告警 + 支持一键重放。时效性没保证（扫描频率低、告警响应慢），但至少不会再出现"三天没人知道"。租约机制是下一个迭代的最高优先级。

## 七、任务依赖：还没开始想的地方

当前所有任务都被视为互相独立的——A 任务跑完了，B 任务不会因为 A 的成败有任何感知。但业务已经在提需求了：数据回填要先回填主表再回填从表、报表生成要等上游 ETL 完成、跨系统的流水线编排。

任务依赖引入的复杂度比前面所有内容加起来都大，列几个还没想清楚的问题：

- 依赖是静态声明在任务上的（"本任务依赖 task X"），还是由调度器动态编排的 DAG？前者简单但无法表达"等一类任务全部完成"；
- 依赖任务失败时，下游是 failed、blocked 还是等待人工介入？不同的业务答案完全不同；
- 依赖链一长，前面一个任务重放，后面整串要不要级联重跑？级联的粒度是什么？
- 依赖关系本身要不要持久化成状态机的一部分，还是靠事件驱动临时聚合？

目前倾向于：依赖关系持久化存储（不然 worker 重启后依赖图重建不出来），调度上仍用"事件驱动 + 状态检查"而非中央 DAG 引擎，保持无中心的简单性。但这个方向没有定论，先记下问题，等租约机制落地之后再专门立项讨论。

## 八、附：现状速览

| 环节               | 现状                                 | 主要风险                       |
| ------------------ | ------------------------------------ | ------------------------------ |
| 状态机与持久化     | 已固化，状态迁移必落库，与业务同事务 | —                             |
| 领取               | 先原子标记 running 再执行            | —                             |
| 幂等               | task_id 持久化去重                   | —                             |
| 超时               | 按任务类型配置，超时标记 failed      | —                             |
| 取消               | 协作式检查点，终态混入 failed        | 取消与失败未拆分               |
| 完成事件           | 落库后发布，失败进补发队列           | 消费者需自行幂等（已遵守）     |
| **崩溃恢复** | 仅扫描 + 告警 + 人工重放             | **最大缺口，无租约机制** |
| 任务依赖           | 未实现，任务视为独立                 | 业务需求已出现，待立项         |

3 月事故沉淀的最后一条原则放在结尾：**"worker 重启"不是异常场景，是日常场景。** 发布、扩容、机器维护，worker 重启天天发生。所有设计评审都应该问一句——"这时候正在跑的任务会怎样？"答不上来的设计，上线之后自然会用事故来回答。
