# Saga 与补偿笔记（跨服务一致性）

> 背景：下单流程横跨订单、库存、支付、风控四个服务。2026-02 的事故：库存扣减成功、支付预下单失败，订单没建上但库存已经扣了——凌晨的库存对账发现差异，手工补偿漏了"释放库存"这一步（因为补偿清单是 Excel 里手抄的），第二天白天的商品全部超卖。这个事故直接触发了跨服务一致性方案的讨论：上 Saga 还是上 TCC，补偿怎么做才不漏。

---

## 一、为什么需要 Saga：分布式下没有本地事务

单机时代的"下单+扣库存+扣款"一个事务搞定。服务拆分后，三个操作在三个数据库，**没有跨库事务**。可选路径只有两条：

- **Saga**：把跨服务流程拆成一串本地事务，每个本地事务配一个**补偿操作**。失败时逆序执行补偿。**最终一致**——中间状态对外可见（库存已扣、订单未建的窗口存在）。
- **TCC**（Try-Confirm-Cancel）：每个服务实现三态接口，全程锁资源，追求更强的中间一致性。**实现成本高**（每个参与方要写三个接口，还要处理空回滚、悬挂等问题）。

订单域的评估结论：**选 Saga**。理由：库存/支付/风控都是幂等改造已完成的服务（幂等笔记的成果），TCC 的强一致收益在订单场景不值它的成本。TCC 留作"将来如果做资金强一致"时的备选。

## 二、Saga 的两种编排方式

- **编排式（Orchestration）**：一个中心 Saga 协调器维护流程状态机，按顺序调用各服务，失败时触发逆序补偿。流程显式、好排查；代价是协调器是新的单点。
- **协同式（Choreography）**：各服务通过事件互相触发（订单创建事件 → 库存服务扣减 → 扣减成功事件 → 支付服务），失败事件触发各自的补偿。无中心、服务自治；代价是流程散落在事件里，出了问题要顺着事件链拼图。

当前选**编排式**：订单服务的 Saga 协调器维护状态机。理由：编排式流程显式，9 月消息事故（消息笔记）证明"散落在事件里的流程"排查成本极高。协调器自身的高可用用订单服务多副本 + 状态持久化解决（状态机落库，与 jobs 笔记的"状态转换必须持久化"同原则）。

## 三、状态机与持久化

Saga 状态机（订单下单 Saga）：

```
CREATED → INVENTORY_RESERVED → PAYMENT_AUTHORIZED → ORDER_CONFIRMED
             │ 失败                   │ 失败
             ▼                        ▼
     INVENTORY_COMPENSATING    PAYMENT_COMPENSATING → INVENTORY_COMPENSATING
             │                        │
             ▼                        ▼
        SAGA_ABORTED              SAGA_ABORTED
```

三条纪律（全部来自 jobs 笔记的同款教训）：

- **状态转换必须落库**，与业务操作同事务——协调器重启后能从库恢复状态机，而不是从头再来。
- **补偿必须幂等**：补偿操作本身可能被重复执行（协调器重试、人工重放），释放库存的补偿重复执行不能变成"释放两次"。补偿用幂等键（幂等笔记）按原操作 ID 去重。
- **补偿的补偿**：补偿也可能失败——补偿失败进补偿重试队列，最终由对账兜底（lock 笔记的三层保障：Saga 是流程层，对账是最后防线）。

## 四、补偿操作的语义

补偿不是"撤销"，是**语义抵消**：

- 库存：扣减的补偿是"回补"（+N），不是物理删除扣减记录——操作历史要保留，审计和对账要用。
- 支付：预下单的补偿是"释放冻结"，真正扣款的补偿是"退款"——退款和释放冻结是不同操作，不能混。
- 幂等记录的补偿：原操作有幂等记录，补偿也要有独立幂等记录，且**补偿和原操作不能共用一个幂等键**（否则"扣了又回补"会被去重成"扣了"）。

## 五、中间状态的可观测性

Saga 的中间状态（库存已扣、订单未建）是**真实存在的业务状态**，不是 bug。但必须可观测：

- 每个状态转换打点（转换名、耗时、来源）。
- **Saga 停留时长监控**：一个 Saga 在中间状态停留超过阈值（当前 10 分钟）就要告警——要么是服务挂了，要么是补偿卡住了。
- 对账兜底：每日对账比对 Saga 状态与各服务的实际状态（库存的扣减量 vs 订单的确认量），差异进对账处理队列。2 月事故的根因之一就是**只有对账发现、没有对账处理流程**——发现了差异，处理靠人。

## 六、已知缺口

1. **补偿框架未实现**：Saga 协调器是手写的，每个流程的补偿逻辑也是手写的——新增一个 Saga 要写全套状态机+补偿。方向：抽象补偿框架（补偿步骤声明式定义、自动重试、自动幂等）。
2. **人工补偿无工具**：对账发现的差异目前靠手工处理（2 月事故的手抄 Excel 就是这个）。方向：对账差异 → 自动生成补偿工单 → 人工审批执行 → 回写结果。
3. **TCC 的适用边界未定**：什么场景值得上 TCC 没有结论。方向：等第一个"需要强一致"的资金场景出现时再评估。

## 七、沉淀

- 跨服务一致性没有免费方案：Saga 换最终一致，TCC 换强一致，成本完全不同。
- 编排式的流程显式性在事故排查时价值巨大——"散落在事件里的流程"是排查噩梦。
- Saga 状态机要持久化、补偿要幂等、补偿还要有补偿——三层防护，最后对账兜底。
- 补偿是语义抵消不是删除历史；补偿和原操作不能共用幂等键。
- 中间状态是合法状态，但必须可观测——停留超时告警是 Saga 的生命体征监控。
