# 幂等设计模式笔记（工程落地）

> 背景：重试笔记（baseline-retry）里写了"幂等键"这个概念页——那是讲**为什么**需要幂等。这篇是**怎么做**：幂等键怎么生成、存在哪、并发场景怎么兜底、记录怎么清理。写这篇的直接原因是 2026-10 的一次线上事故：支付回调的幂等记录用的是"回调流水号"，但第三方支付平台对同一笔支付的**重试回调会换流水号**——去重键选错了，同一笔支付被处理了两次，客户被扣了两笔（对账发现后退款）。选错幂等键的代价是实打实的资金事故。

---

## 一、幂等键的生成：键要对，不只是有

事故复盘的核心结论：**幂等键必须是"业务操作的固有标识"，不能是"某次请求的标识"**。

- 支付回调：业务固有标识是支付平台的**支付单号**（同一笔支付的任何重试回调都带同一个支付单号）；"回调流水号"是每次请求生成的，重试就变——选它就等于没有幂等。
- 下单请求：业务固有标识是客户端的**订单号**（客户端重试复用同一个订单号）；HTTP 请求 ID 每次不同，不能用。
- 对账任务：任务 ID（jobs 笔记的任务幂等）。

判断标准一句话：**问"这个操作重复发生的根源是什么"，用根源的标识做幂等键**。操作因重试而重复 → 用重试复用的标识；操作因消息重投而重复 → 用 message_id（消息笔记）；操作因人工重放而重复 → 用任务 ID。

## 二、幂等记录的存储：介质与窗口匹配

幂等记录存哪，取决于**重复可能在什么时间尺度发生**：

- **进程内去重**（内存 Set）：只能挡住同一进程内的即时重复。进程重启、多实例部署下完全失效。**当前禁止在生产使用**——jobs 笔记的教训（内存去重表在重启后导致重复执行）已经吃过一次亏。
- **Redis**：适合短窗口（分钟到小时级）的高频幂等。当前支付回调的幂等记录在 Redis，TTL 2 小时。
- **数据库唯一约束**：适合长窗口（天级到永久）的幂等。当前订单表的 `order_no` 唯一索引就是天然的幂等兜底——**幂等键落库加唯一约束，是最后一道防线**。

Redis 和 DB 不是二选一，是两层：Redis 挡高频重复（快），DB 唯一约束兜底（慢但绝对）。Redis 的记录丢了没关系，DB 唯一约束还在。

## 三、并发幂等：唯一约束与 fencing

同一幂等键的两个请求**同时到达**时，先查后写有竞态（两个都查到"不存在"，都执行）。解法：

- **唯一约束兜底**：业务表幂等键唯一索引，第二个写入直接失败，回滚并查询已有结果返回。这是最可靠的，当前主方案。
- **分布式锁**：处理前抢锁（lock 笔记的 Redis 锁）。但锁只能串行化，不能替代唯一约束——锁过期（GC 停顿）后并发仍会发生，锁笔记的 fencing 缺口在这里同样适用。
- **fencing/epoch**：带版本号的写入，旧持有者被资源方拒绝。锁笔记的缺口 1，在幂等场景同样需要。

当前状态：唯一约束兜底已实现；锁+幂等的组合只在支付回调路径使用；fencing 未实现（与锁笔记缺口一致）。

## 四、幂等与重试的边界（重申但落地）

重试笔记的边界是"错误码决定该不该重试，幂等决定重试安不安全"。落地到代码层面：

- 重试框架**不持有**幂等键——它不知道业务标识是什么。
- 业务层在发起写请求时**显式传入**幂等键，服务端按键去重。
- 没有幂等键的写请求，重试框架应该**拒绝重试**（宁可报错也不赌"上次没生效"）——当前这条还没实现，重试框架现在对无幂等键的写请求照常重试，这是待修项。

## 五、幂等记录的清理

幂等记录会越积越多（尤其是 DB 唯一约束是永久的——那是业务数据的一部分，本来就要留）。Redis 层的清理策略：

- TTL 覆盖重复窗口即可：支付回调的第三方重试窗口是 2 小时，TTL 就是 2 小时。
- **TTL 过短的风险**：重复发生在窗口之后，幂等失效——第三方平台超过 2 小时的重试回调极少但存在，这种"超窗口重复"要靠对账兜底（lock 笔记的三层保障：锁+幂等+对账，幂等不是最后一层）。
- **TTL 过长的代价**：Redis 内存。当前 2 小时 × 日峰值 50 万回调，内存可控，暂无压力。

## 六、已知缺口

1. **跨服务幂等无标准**：订单域自己定了幂等键规范，但支付、风控各有一套。跨服务调用时幂等键怎么传、键的命名规范——没有约定。方向：出幂等键规范文档 + 请求头约定（`Idempotency-Key`）。
2. **无幂等键写请求的重试拦截未实现**（第四节说的待修项）：重试框架目前不区分"有幂等键的写"和"无幂等键的写"。
3. **幂等键变更的迁移路径**：如果发现某个键选错了（像 10 月事故的流水号），线上已有数据怎么迁移——没有方案。方向：幂等键变更 = 新键从新数据开始 + 旧键保留窗口 + 对账兜底。

## 七、沉淀

- 幂等键是业务操作的固有标识，不是请求标识——选错键等于没有幂等。
- 幂等记录分两层：Redis 挡高频（快）、DB 唯一约束兜底（绝对）。
- 并发幂等的唯一可靠解是唯一约束；锁和 fencing 是加速和补充，不是替代。
- 幂等不是最后一层防线——超窗口重复由对账兜底。
- 没有幂等键的写请求，重试框架应该拒绝重试。
