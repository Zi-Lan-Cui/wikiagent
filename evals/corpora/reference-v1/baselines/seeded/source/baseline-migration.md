# 数据库迁移笔记（订单服务实践）

> 背景：订单服务常年在演进——加字段、拆表、调索引——schema 变更和代码发布交织在一起，是这个服务最容易出事的交叉地带。最近一次迁移把发布顺序搞反了，服务短暂 500；往前追，2026-02 的事故性质更严重：收缩操作先于新代码发布执行，删列比新代码上线早了一天，旧代码的插入语句直接报错，订单写入中断。两次事故都指向同一件事：**数据库变更和代码发布的顺序不是细节，是生死线**。这篇笔记固化三阶段流程、回填与回滚的做法，以及多服务共享数据库这个最没把握的缺口。

---

## 一、核心心智模型：把 schema 变更当成一次航行，不是一次跳跃

事故之前对迁移的想象是这样的：改表、改代码、一起上线，干净利落。两次事故之后，想象被修正成：schema 变更是一次需要**逐步换舷**的过程——旧结构和新结构要在水面上并存一段时间，流量从旧结构淌到新结构，确认旧船没人了，才能凿沉它。

这个心智模型直接推出后面的一切：为什么只能按固定顺序走、为什么删除必须最后、为什么兼容性以旧代码为准、为什么回滚回的是代码不是数据。它们全是同一条逻辑的推论：**在任何一个中间时刻，系统都必须能用"当前已发布的任意版本代码"加"当前已执行的任意子集变更"正常运行。** 做不到这一点的变更设计，就不是在部署，是在赌。

## 二、三阶段顺序：扩展 → 迁移 → 收缩

### 2.1 扩展（Expand）：只做加法

第一阶段只对数据库做加法：新增列、建新表、加索引。铁律是所有变更必须**向后兼容**——已经在线上跑的旧版本代码，面对变更后的数据库，读写行为要和变更前完全一致。

这条铁律有一个经常踩的具体坑：**新增列必须有默认值或允许 NULL**。直觉上"新列非空"更干净、更符合最终态的设计洁癖，但旧代码的插入语句根本不知道该列的存在，不会给它赋值——非空约束一上，旧代码每次插入都炸。2 月事故的剧本正是这个的变种：不是加列，是删列，但性质相同——数据库的约束和旧代码的假设发生了冲突。兼容性的全部工作，就是消除这类"数据库已变、代码未变"的冲突窗口。

### 2.2 迁移（Migrate）：数据搬家，新旧并存

第二阶段做数据层面的搬家：把旧结构的数据回填到新结构，需要双写的场景在新旧结构间建立同步。这一阶段新旧结构**同时存活**，读可以切、写可以双写，任何一个环节出问题都可以退回旧路径。回填的具体做法见第三节。

### 2.3 收缩（Contract）：确认无人使用，才删除

第三阶段删除旧结构。这是整个流程里**唯一危险的阶段**——扩展搞错了是兼容性问题，收缩搞错了是可用性事故。2 月事故的完整剧本：团队计划"先收缩后发布"，理由是"新代码反正明天就上，提前一天删列省得再跑一趟"。结果发布延期了——发布延期的概率从来不为零——旧代码多跑了一天，对着一个不存在的列执行 INSERT，报错，订单写入中断。

删除的安全姿势被固化为一条流程：**先发布不再引用旧结构的代码版本，观察至少一个完整发布周期，确认旧结构的访问计数归零，再执行删除。** "完整发布周期"是最低要求而不是建议值——发布系统有灰度、有分批，一个周期意味着所有实例都轮换到了新版本、所有可能的旧实例都已退出。心跳残留、忘下线的灰度实例、定时任务跑在旧版本上，这些"看不见的引用方"都需要一个完整周期来自然暴露。

判断"无人使用"的标准也要写死：**看监控指标里的旧结构访问计数，而不是在代码仓库里搜引用。** 搜索只能覆盖仓库内的静态引用——动态拼接的 SQL、存储过程、BI 直连、运维脚本的临时查询，全都搜不到。访问计数是运行时事实，代码搜索是编译时猜测，用猜测给删除操作开门，事故只是时间问题。

## 三、数据回填：两种姿势，一种心态

回填的目标是让新结构的数据完整到可以接管读流量。两种实现方式适用于不同场景。

**批量回填**适合数据量大、切换时间紧的场景——几百上千万行订单记录，等懒回填慢慢补要到下个季度。工程上的几个要点：小批量循环（每批几百到几千行），避免一个吞掉整个表的长事务，长事务既撑爆 undo log 又锁着行阻塞业务写入；进度按主键游标记录，**可中断续跑**——回填跑几个小时是常态，中途发布、扩容、抖动都可能打断它，从游标续跑意味着中断的代价是几分钟而不是从头再来；批次之间留一点间隔或让出资源，别和业务高峰期抢 IO。

**懒回填**适合访问分散、等得起的场景：读路径发现新结构缺数据，顺手补写。它的优点是不用大迁移、天然按访问热度排序（热数据先补完），缺点是不被访问的冷数据永远是缺的——如果切换后有人去翻三年前的订单，懒回填就来不及了。所以懒回填要配一个兜底：超过一定期限冷数据占比还高，就转批量回填收尾。

当前以批量回填为主，理由是订单数据的访问模式经不起"冷数据缺失"——客户投诉、财务对账都会直捣冷数据区。懒回填更适合用户画像、推荐特征这类"近期活跃才重要"的数据。

**共同的心态**是：回填是重操作，重操作就要可中断、可限速、可观测。回填任务本身要有进度打点、速率监控、错误隔离（单行失败记日志跳过，不能因为一条脏数据卡住整批）。

## 四、回滚：回滚代码，不回滚数据

回滚策略遵循一条反直觉但极其重要的原则：**结构变更尽量做成"旧代码仍可用"的形态，出问题时回滚代码版本，而不是回滚数据。**

原因要从两种回滚的成本对比来理解。代码回滚是分钟级的、已被演练过无数次的操作——回滚到上一个发布版本，服务立刻回到已知良好的状态。数据回滚呢？正向迁移改了几亿行数据，逆向改回去又是一轮同等规模的重操作，而且正向迁移期间新写入的数据往哪儿去？正向和逆向转换叠加，极易造成**数据漂移**——两边转来转去，某些行经历了偶数次还是奇数次转换，最终状态无法确定。所以规范明确：**已执行的数据回填不做反向回填**。数据错了有数据订正脚本（针对性修，不做全量逆向），服务错了回滚代码。让两个层面的回滚各自保持简单，而不是设计一个同时回滚两者的"超级回滚"。

这条原则反过来约束了变更设计：任何"做了就回不去"的 schema 变更（比如直接改列类型、原地拆表），都必须先改造成扩展-迁移-收缩的形态才能上线。**回滚能力不是运维给的，是变更设计时就用兼容性换来的。**

配套的一条保障：删除操作执行前必须有**快照**，快照保留期覆盖整个观察期。万一收缩阶段误删了还有引用的结构，快照是最后的后悔药——从快照恢复比从备份恢复快几个数量级。保留期要写明"超过观察期后才能清理"，不然磁盘报警一来，有人顺手把"已经没用了"的快删了。

## 五、兼容性判断：以旧代码为准

整个体系里最容易想反的一个判断：**兼容性的标准是"旧代码能跑"，不是"新代码能跑"。** 新代码是跟着新 schema 一起设计的，它当然兼容新结构——这个判断没有信息量。有信息量的问题是：数据库已经变了、代码还没变的那段窗口里，旧代码会不会挂？

顺着这个标准，几条具体操作纪律：

- 加列：可空或有默认值（已述）。
- 改语义：旧列含义变更时，新语义用新列承载，旧列保留旧语义直到收缩，禁止"同一个列悄悄改变含义"——这种变更没有任何一版代码能兼容。
- 加索引：纯加法但非无代价，写入高峰期建索引会锁表或拖慢写入。安排在低峰执行，执行期间观察写入延迟曲线，超阈值就暂停。
- 拆表：新表建好、双写跑稳、读流量切换、观察、停写旧表、再删除——一步都不能并。

最后一条几乎就是整篇笔记的缩影：**每一步变更都能独立回滚，不能设计成"三步必须一起完成"。** "必须一起完成"的三步，本质是把一次航行拆成了三次跳跃。

## 六、扩展和迁移能否合并？

FAQ 里被问最多的问题，单独回应一下。

支持合并的论据是真实的：扩展和迁移分开，意味着新旧结构并存的时间拉长，双写逻辑要在代码里多活一个发布周期，流程总时长被拖长；很多变更其实很简单——加个带默认值的列、建张一次性的中间表——为它们走完整三阶段有形式主义之嫌。

但规范的判断是**不合并**，理由不在简单变更上，在流程的博弈结构上。三阶段拆开，每个阶段的入口都是一次明确的决策点：扩展合入前评审兼容性，迁移启动前确认扩展稳定，收缩执行前核对访问计数。合并之后，这些决策点压缩成一次"把变更和数据一起上"的操作，出问题时的排查面是结构、数据、代码三者的笛卡尔积，回滚的粒度也跟着消失——回滚代码会留下没回滚的数据，不回滚代码就得带着可疑的数据继续跑。2 月事故已经证明，**流程里多出来的那几天"麻烦"，就是留给发现和纠错的缓冲带**。为简单变更省几天的代价，是让所有变更失去这道缓冲。

折中的出路不是合并阶段，而是**给简单变更一条快车道**：带默认值的可空加列、纯新增索引这类零风险扩展，走简化的审批和观测流程，但仍然作为独立的扩展阶段存在——快车道压缩的是流程开销，不是顺序本身。顺序是安全性的来源，开销是管理的成本，把成本降下来可以，把来源拆掉不行。

## 七、已知缺口

**多服务共享数据库的发布顺序，是当前体系里最薄弱的一环。** 订单库不只订单服务一个使用者——报表服务直连、对账任务直连、几个老服务还共用着几张表。三阶段流程保证的是"单个服务的代码版本"和"数据库变更"之间的兼容，但当**多个服务的代码版本**和同一组变更排列组合时，"哪个服务先发布、哪个后发布、谁先谁后才能保证每个中间态都有解"，没有成文约定。当前靠口头同步："这次改表，A 服务先发，B 服务第二天发，第三天我删旧列"——服务两三个的时候口头同步勉强够用，服务一多、发布一频繁，总会有一个人没被同步到。2 月事故的直接原因表面上是顺序搞反，往深一层挖，是**顺序依赖存在于人的记忆里而不是系统的约束里**。

想过的改进方向：给共享表维护一张"引用方清单"，每次变更自动通知清单上的所有服务负责人，各自的发布窗口和确认回执留痕；更重的方向是 schema 级别的契约测试，每个服务跑 CI 时验证自己对 schema 的假设和当前定义一致。都还没落地，先记为最高优先级的流程债。

**收缩阶段的删除没有自动化闸门**是第二个缺口。访问计数核对、观察期满确认、快照存在性检查，目前是一张 checklist 加一个人工"确认执行"。人工确认在长链条里是最不可靠的一环—— checklist 会疲劳，确认会流于形式。想做的闸门不复杂：删除命令执行前自动校验三项前置条件（访问计数归零满一个周期、快照存在且在保留期内、变更单上所有引用方已签收），任何一项不满足直接拒绝执行。把"人记得检查"换成"系统强制检查"，和日志规范里脱敏下沉框架层是同一个哲学。

## 八、沉淀

两次事故合成一句话：**数据库变更的事故，绝大多数不是技术难题，是顺序失守和引用漏判。** 顺序失守靠三阶段流程兜底——固定顺序、删除压轴、观察期靠计数不靠搜索；引用漏判靠闸门兜底——只是闸门还没建。而流程性失守（口头同步的顺序、人工执行的检查）最终都要落成系统性约束，这大概是这几篇笔记反复出现的一条共同主线了。
